# Real Electron functional regression guardrail

Build once, then run the complete guardrail without a live TV:

```sh
corepack enable
yarn install --immutable
yarn playwright install ffmpeg
yarn build
yarn test:integration
```

On Linux, use `xvfb-run -a yarn test:integration`. CI installs Xvfb/Xauth, ZIP/unzip and Electron GTK/NSS/GBM/audio dependencies. The `integration` job has no job-level skip condition; the final build depends on it. GitHub's workflow-level skip directives and repository branch-protection settings remain platform controls. `yarn typecheck:integration` checks all runner, fixture and independent emulator TypeScript. The runner pins Playwright 1.64.0, uses Electron from the repository, one worker, no retries and `forbidOnly`. All nested emulator `.spec.ts` files run in this same command.

After upgrading Playwright, rerun `yarn playwright install ffmpeg`: the runner selects its own encoder revision (1013 in 1.64.0), independently of the repository's Electron version. Electron video capture still uses the real application window and the encoder selected by Playwright; no bundled Playwright browser replaces Electron.

**Full-suite platform prerequisite:** mandatory Linux CI runs every scenario, including real migration between `127.0.0.1` and `127.0.0.2`. A local macOS run needs the second IPv4 loopback alias assigned by the operator beforehand; otherwise the OS rejects binding `127.0.0.2` (`EADDRNOTAVAIL`) and that scenario fails rather than skipping or faking migration. The runner never changes user network configuration. No IPv6 discovery support is implied.

## Boundary and cleanup contract

`app-harness.ts` launches `_electron.launch({args:[repository,...]})`: package.json's actual main entry, actual compiled preload and the built `dist/index.html` renderer. There is no replacement app, adapter, IPC handler, business success stub or dependency codec in the TV emulator. Tests interact with the DOM or `window.gtvRemote`, the production public preload surface. Electron native APIs are used to inspect window state, reserve a conflicting global shortcut and crash the actual renderer.

Every case owns a `mkdtemp` profile below `os.tmpdir()`. `--user-data-dir` and `GTV_INTEGRATION_CONFIG` select that profile before production stores initialize. Config schemaVersion 1 includes pairingPort, remotePort, discoveryCommand, discoveryStatePath, systemStatePath and dialogStatePath. Runtime rejects packaged use, non-temporary profiles, paths outside the profile, non-loopback endpoints and foreign renderer IPC. Fixture executables may reside in this repository.

Integration configuration optionally accepts `discoveryPlatforms: string[]`. Entries must name registered providers. Omission preserves the Google regression suite's `['google-tv']` discovery scope; an empty list disables discovery, while explicit lists select real provider discovery implementations. This setting does not remove providers or replace pairing, connection, or command transports: saved Apple/Fire devices remain usable in isolated wire tests. Production scans all registered providers. Google fixture discovery tests do not establish Apple/Fire native discovery correctness or physical-device interoperability.

`STARTUP-SINGLETON` launches a real second Electron child with the first main process's application arguments, working directory, isolated profile and integration environment. Playwright strips inherited `NODE_OPTIONS` from its first launch, so the raw child must strip it too; Playwright's debugger/loader arguments are not application arguments and are not replayed. Success requires the original window to be currently visible **and focused**, with exactly one window, plus a normal child exit code of zero. Startup focus/show observations cannot satisfy this assertion after the explicit hide. A `singleton-launch-diagnostics` attachment records allowlisted launch arguments, first-process lock ownership, singleton symlink paths/targets, child exit/signal/error and bounded sanitized stdout/stderr; it never reads credential files or dumps the environment. Environment parity is a driver invariant, not proof of the cause of a native singleton failure.

Pairing first attempts a refused real loopback port. Production generates its own certificate in `<profile>/androidtvremote/<safeKey>.cert.pem` and private key beside it. The harness reads only the public certificate, explicitly trusts it in the emulator, starts TLS listeners and retries. The emulator requires and verifies the app's client certificate; the actual application retains its production `rejectUnauthorized: false` behavior and does not verify the server certificate's trust chain. The real pairing exchange independently binds both certificates' RSA public keys to the six-hex pairing code, and remote access additionally requires successful pairing. Separate independent raw TLS-client tests verify certificates in both directions. No private key, certificate dump or profile dump is attached to results.

The emulator allocates adjacent endpoint pairs in `16000–23999`, below the default automatic TCP client-port ranges on Linux (`32768–60999`) and macOS/Windows (`49152–65535`). Allocation binds the actual TLS listeners; it does not discover ports with `listen(0)` and release a separate probe. An exclusive pair directory under `os.tmpdir()/gtv-emulator-endpoints` remains owned until emulator disposal, including initial pairing refusal, refusal faults and host migration, so concurrent fixture processes cannot allocate a temporarily closed endpoint. Only the fixture's own empty lease directory is removed; unknown/stale leases are never reclaimed. Hosts with a customized automatic client-port range overlapping this pool are outside this fixture contract.

`refuse` destroys established and pre-handshake TCP/TLS sockets, closes both listeners and awaits their close events before returning. Restoring the TV binds the same leased endpoints without retries or suppression of bind failures. A closed `listen(0)` endpoint could become a reconnecting loopback client's source port (or its `TIME_WAIT` endpoint), making the listener's restoration fail with `EADDRINUSE`; the low pool prevents that automatic client-port ownership transition. Refusal still comes from the real OS socket boundary, produces terminal production connect-failure metrics, and recovery must deliver a real key command to the same TV. The existing transport-fault scenario also allocates a second emulator during the refused interval to exercise fixture isolation.

The native discovery process uses `GTV_DNS_SD_STATE`; the production DNS-SD parser receives synthetic Remote/Cast/ADB browse, resolve and address output. Native system JSON is `{loginSupported:boolean,login:boolean|null,loginGetError?:string,loginSetError?:string,microphone:'granted'|'denied'}`. Native dialog JSON is `{responses:number[],requests:MessageBoxOptions[]}`; queued numbers choose buttons, missing responses fail explicitly and requests are recorded. Native preference precedence and all application decisions run normally; shortcut ownership is real Electron registration.

RESET fixtures the renderer's `window.confirm` OS decision with explicit cancel/confirm responses. Both reset-button clicks, the production handler/preload/IPC, store mutation and credential deletion remain real. CDP-dismissed physical Electron dialogs did not reliably restore native focus, so this case does not claim physical dialog/focus recovery. Cancellation preserves complete device records and the certificate; deletion requires actual absence (`ENOENT`), not an arbitrary filesystem error.

The integration-only main-process `getIntegrationTrayMenu()` observes the same real Electron Menu installed on the real Tray. The harness selects stable native MenuItem IDs (`show-remote`, `hide-remote`, `check-updates`, `quit`) using their actual registered click callbacks. Only physical OS menu selection is simulated; production menu handlers, updater dialogs, state transitions, UI effects and process termination remain live. There is no private app-handler replacement or renderer backdoor.

Chromium's file-backed fake microphone reads a deterministic mono PCM16 WAV, 48 kHz, four seconds, 440 Hz sine at amplitude 0.25. The actual `getUserMedia`, renderer downsampling/PCM encoding, preload/IPC and TLS pipeline run. The TV checks session order, chunk bounds, 8 kHz PCM16LE, RMS and frequency rather than accepting arbitrary nonempty audio.

Negative-only media OS fixtures make `navigator.mediaDevices.getUserMedia` throw a `NotFoundError` or native `AudioContext.resume` reject in explicitly named cases. These model unavailable device/audio-start conditions; no fake successful stream/audio is returned and no app capture/downsampling/voice/business function is replaced. The actual renderer handles errors and cleanup. A real renderer reload removes each negative-only override; the recovery path again uses genuine Chromium `getUserMedia`, the WAV and protocol waveform assertions.

Updater config adds `{releaseApiUrl,installedBundlePath,commandExecutable,relaunchStatePath}`. Releases/downloads are real loopback HTTP. ZIP extraction, backup, directory replacement, rollback and updater-state persistence are real sandbox filesystem operations. `os-tools.cjs` supports ditto/unzip/copy, rm, quarantine-clear metadata and loopback-only external-open metadata, rejects escaping paths/symlinks and records command arguments. Relaunch metadata is `{requested:true,installedBundlePath,version}`; the subsequent actual app launch reads installed Info.plist version. Fixtures never invoke the production GitHub API, `/Applications`, a real browser or OS login preferences. Without an updater provider, integration update checks cannot contact production GitHub.

Teardown closes the actual Electron app, emulator TLS listeners/sockets and loopback HTTP server, then deletes each temporary profile, including on assertion failure. Failure artifacts include renderer screenshots, Playwright trace, video, sanitized protocol state/message summaries and native window-event observations. Native observations record focus/blur/show/hide/close/unresponsive/navigation timestamps, actual default global-shortcut registration and actual Chromium media-permission handler requests; they do not replace app methods. Profiles, WAV/ZIP payloads and credentials are not uploaded. The one-time Playwright ffmpeg dependency install is allowed to fetch an encoder; actual app/test fixture networking remains loopback only.

## Regression invariants

- Voice sessions belong to one live connection. Expired PCM, stop and pending-state queries cannot reconnect an old session. A rejected audio queue still releases capture and backend state; the next recording succeeds in the same renderer.
- Forget removes the device's local certificate/key and closes matching cached sessions, including migrated host identities, without deleting another device's credentials. It does not claim to remove the TV's own pairing records.
- Command counters remain cumulative while recent history stays bounded to 40 records. Delayed admissions and drop bursts cannot evict the active serial send before its terminal accounting.
- Tab and Shift+Tab cancel shortcut capture, restore native shortcut ownership and move focus after asynchronous restoration; deliberate recorder re-entry pauses ownership again.
- Native fixture JSON is published by exclusive sibling-file creation and atomic rename. Failed publication preserves complete prior state and cannot delete a competing file.
- IME metadata is emitted only when negotiated. Restored text setup waits for a real ordered ping response after metadata, not merely connection readiness; stale counters still fail the independent TV oracle.
- Coalescing writes the remote-start and negotiated IME frames together; fragmentation splits the complete transmission. Text acceptance still requires both frames to be decoded and their metadata consumed, rather than merely a successful connection.
- Native quit is checked through the real child-process handle captured while Electron is live. Teardown does not query Playwright's disposed process channel after exit, and setup failures retain sanitized diagnostics.

## Coverage matrix

Scenario IDs below are test title prefixes, not source-wording or screenshot-geometry assertions.

`PAIR-CHECKSUM` enters an independently wrong hexadecimal checksum through the actual renderer and clicks Connect. It requires the visible certificate-hash error, return to the device picker, no transmitted pairing secret and no authorization. Clicking the discovered device again must establish a fresh TLS pairing session with an empty code field; entering that session's correct code must authorize and connect, and clicking Select must change the independent TV model. This checks rendered local-checksum recovery, not physical Streamer firmware interoperability.

`RESET` waits for the renderer's paired-device list to clear and Reset to become enabled after its awaited IPC operation, then checks current and legacy credential deletion. A concurrent bootstrap call can observe the emptied device store before legacy cleanup finishes; it is not a reset-completion signal. The test retains immediate filesystem absence assertions after the actual consumer completion boundary, without sleeps, deletion polling or retries.

## Narrow fidelity limits and current source boundaries

This is a functional regression guardrail, not a hardware/interoperability guarantee. Real Google TV firmware versions, vendor-specific remote features, network multicast behavior, real Bluetooth/Wi-Fi changes and TV microphone interpretation still require individually targeted physical-device checks. Synthetic wire messages and labels are not user captures.

Physical native dialog appearance/post-dismiss focus recovery, Login Items service writes/permissions, menu-bar placement/physical tray selection, system-wide physical shortcut delivery, TCC/device selection, signed installer/quarantine/Gatekeeper behavior, launching an actually installed signed `.app`, and a browser/DMG mount are native boundaries. Fixtures preserve application choices, execute real installed menu callbacks and assert concrete sandbox disk/relaunch metadata; they do not certify these physical OS effects. Automated tray tests simulate OS selection only, not the underlying application action.

`GoogleTvProvider.capabilities` advertises textInput/powerToggle unconditionally. WIRE-CAPABILITY-ABSENCE tests real reduced server negotiation and recovery, but does not claim the production UI hides text based on Google server negotiation. `TvAdapter` and the renderer enforce each provider's advertised command, text, power and microphone capabilities. The existing updater reads `skippedVersion` compatibility state but has no UI/public writer; UPDATE-LEGACY-SKIP explicitly seeds historical input and does not invent a user-facing skip action. Negative-only missing-device/native-start errors exercise the production capture error path; physical microphone selection/removal still requires a native check. Reachable failures remain hard assertions, never `test.skip`, conditional green tests or business-method mocks.

The adopted [LibreControl 1.0.2](https://github.com/LibreControl/google-tv/releases/tag/1.0.2) retains the immediate text-readiness and connection-lifecycle fixes from 1.0.1 and corrects odd-length RSA modulus encoding without weakening certificate-bound checksum validation. Upstream real-TLS regressions independently derive expected hashes from unsigned JWK integers and separately exercise genuine 2049-bit client and TV certificates; both failed before the fix and passed afterward. Its 31-test suite also covers delayed/nonzero and zero IME metadata, pending-text closure/reconnect and unsupported IME behavior. This desktop suite still uses an ordered transport setup barrier for the restored-capability scenario and exercises the published dependency through the actual Electron application; it does not claim that scenario independently proves the upstream immediate-readiness contract. The reported Streamer hash failure has no same-session certificate/code vector, so this demonstrated RSA defect is not an established diagnosis or resolution of that hardware report.

## Multi-TV spike

`multi-tv.spec.ts` runs the real Fire TV provider and locally patched library
through Electron IPC against an independent loopback HTTP/HTTPS receiver and
separate HTTP DIAL endpoint. It models PIN display/verification, authentication
tokens, status, keyboard state, key events and text. The DIAL case accepts launch
before its native TCP listener starts, covering cold pairing and token-based
reconnect without PIN retries. Assertions also cover activation failure preventing
native requests, credential-free DIAL headers, no activation for direct/mDNS
records, wrong-PIN recovery, cancellation, credential restoration after restart,
Unicode text, unsupported volume/microphone rejection, same-host platform
identities and switching away from an active Fire session.

The receiver is not Fire OS. It does not establish SSDP/mDNS discovery, physical
DIAL interoperability, certificate trust provisioning, voice or hardware coverage.
An independent Apple AirPlay receiver additionally exercises `/pair-pin-start`
and initial pair-setup M1/M2 through the real provider/library. An existing corrupt
encrypted credential must not block this fresh PIN request. Cancellation closes
the stage and rejects a late submission without another wire request. This does
not emulate SRP proof, encrypted AirPlay/Companion authentication or completed
pairing; unit tests separately cover two-step pairing presentation.
Production packaged-app discovery was separately observed against
physical Apple TV and Fire TV devices. These fixtures do not perform physical
PIN pairing. Separately, a paired physical Apple TV was reconnected through the
packaged app, and renderer H/mouse Home taps, holds and blur cancellation were
exercised using its native transport. TV-screen state was not captured. This
does not certify the complete hardware feature matrix. Keychain-unavailable
credential behavior is not exercised by the wire fixture.
